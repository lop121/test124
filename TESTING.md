# Матрица проверки

Все строки E2E проверяются HTTP-запросами к работающему Compose-стеку.
`scripts/check.sh` запускает собственный Compose-проект и завершает проверку при
первой ошибке. Проверки БД дополняют, а не заменяют HTTP-проверку результата.
PostgreSQL для pytest отдельный, его имя обязательно заканчивается на `payments_test`.

| Сценарий | Проверяемый результат |
| --- | --- |
| Без ключа / неверный ключ | 401 у API, health и OpenAPI |
| Валидный POST, RUB/USD/EUR | 202, UUID, pending, created_at; точная Decimal и JSON в GET |
| Отсутствие описания и metadata | Допустимые значения по умолчанию |
| Конкурентный одинаковый ключ | Все ответы с одним payment_id, одна строка платежа и outbox |
| Повтор ключа, другой payload | 409, прежний платёж не меняется |
| Повтор ключа, эквивалентный масштаб Decimal | Один платёж |
| Нет Idempotency-Key / пустой ключ / слишком длинный ключ | 422 |
| Нулевая/отрицательная/слишком большая сумма, лишние дробные знаки, NaN | 422 |
| Неизвестная валюта, слишком большие metadata, лишнее поле | 422 |
| Некорректный URL, чужой хост, credentials, fragment, порт | 422 |
| Нет платежа / некорректный UUID | 404 / 422 |
| Успех шлюза | GET succeeded; webhook с верной HMAC-подписью и точными данными |
| Отказ шлюза | GET failed; уведомление об отказе успешно доставлено |
| Две ошибки webhook, затем успех | Три HTTP-попытки, задержки 2 и 4 секунды, одна оплата |
| Постоянная ошибка webhook | Три попытки, финальный статус платежа сохранён, событие в DLQ |
| Webhook отвечает redirect | Переход не выполняется, три попытки, DLQ |
| Дубли RabbitMQ | Финальный статус и число webhook не меняются |
| Невалидное сообщение / повреждённый JSON / неизвестный payment_id | Сообщение попадает в DLQ, следующее обрабатывается |
| Outbox-процесс остановлен | POST принимается, GET pending; после запуска — доставка |
| RabbitMQ остановлен | POST принимается, GET pending; после запуска — доставка |
| Consumer перезапущен во время обработки | Платёж завершается, результат не меняется |

Дополнительно pytest на PostgreSQL проверяет атомарный откат платежа вместе с outbox,
`SKIP LOCKED` между двумя издателями, сбой после publish до commit, сбой после
сохранения результата шлюза, стабильность тела и подписи webhook, ограничение
технических ошибок шлюза тремя попытками. Alembic проверяется upgrade → check →
downgrade → upgrade на отдельной тестовой БД.

Здесь один клиент со статическим ключом, как в ТЗ. Мультиарендность и роли не заявлены.
Тестовые платежи с заданным исходом шлюза создаются непосредственно в БД с outbox
одной транзакцией; это только подготовка данных. Их обработка проходит через
настоящий RabbitMQ, consumer и HTTP webhook, а результат читается через GET API.
